# SAL-150 정산 읽기/쓰기 절감 검증

## 적용 범위

- A: 노선 버전별 PENDING 존재 여부 조회.
- B: 노선/KST 도착일/예보 거리별 당일 합계 증가분을 한 번씩 저장.
- C: 정산100건씩 저장. 입력의 예측/도착 관측 ID를 합쳐 중복을 제거하고, 품질을 통과한 관측을 묶음 안에서 한 번 읽어 재사용. 입력 키 중복은 기존 순차 처리. 반환은 입력 순서로 정렬.
- D: 조회한 PENDING 키 중 조사 완료(DONE)와 EXCLUDED 편도가 모두 확인된 평가만 QUALITY_EXCLUDED로 종료. 같은 차량/노선의 재조사가 진행 중이면 유지. 노선 버전당 한 번에500개 이하. 원본 관측과 기존 확정 정산은 보존.
- E: 기존 PENDING 부분 인덱스 유지.
- F: 기존 autovacuum 설정 유지.

## 읽기량과 속도는 구분

정산은 fixedDelay60초이므로 처리시간이 짧아지면 시간당 실행 횟수는 늘 수 있다. 다른 작업의 지연이 없다는 가정에서 시간당 실행 횟수는3600/(60+처리시간)이다. 처리시간만으로 시간당 DB 읽기가 줄었다고 판정하지 않는다. PENDING 목록을 매 회차 처음부터 읽는 방식은 남아 있으며, D는 그중 다시 처리할 수 없는 확정 제외분을 점진적으로 제거한다.

배포 전후에는 같은 시간대/노선 수/정산 처리량 기준으로 settlement_tick/settlement_save, 시간당 RDS ReadThroughput 적분값, I/O, 처리량 크레딧, 정산 지연/PENDING 적체를 함께 본다. 기존 느린 작업 로그는 임계값 이상 표본이므로 전체 평균/실행 횟수로 해석하지 않는다. 정상 PENDING 수요가 크면 제외 처리만으로 해결되지 않을 수 있다. settlement-interval 인상은 정산/당일 보정 지연과 함께 별도 결정한다.

## 로컬 실험

PostgreSQL18/1CPU/768MiB/shared_buffers88MiB/work_mem4MiB, V1~V27 실제 스키마. 합성 데이터이며 운영 복제본이 아니다.

A: 노선 버전4개/PENDING6만건에서4.065→0.032ms.10,004버전에서는4.194→5.930ms로 역전했다.

B: 실제 서비스/저장소 기반 입력3,000개 중 초기화된 노선2,004개를24그룹으로 합산.393.588→6.267ms/WAL320,160→6,784bytes. 합산 순서에 따른 확률 합 최대차약7.1e-15.

C: 관측300,250개/평가360,000개/정산3,000개. 단순 묶음100개는 전체101.100ms, 관측 중복 제거를 포함하면67.684ms(각3회 중앙값). 같은 실험 회차의 기존1건씩 방식은1,765.991ms. 실행시간에는 JDBC 호출/반환/커밋이 포함된다.

별도100건 EXPLAIN ANALYZE 표본에서 단순 묶음→관측 중복 제거:
- 관측 인덱스 탐색200회→18회
- 관측 노드 shared hit800→72
- 전체 shared hit4,827→2,744
- shared read0/temp write0(두 경우 모두)

위 블록 수는100건 SQL 한 번의 버퍼 접근이며3,000건 전체나 물리 디스크 읽기량이 아니다. WAL 감소를 주장할 근거도 없다. cold cache/운영 동시 부하는 재현하지 않았다.

E: 기존 합성 dirty fixture에서 정렬 인덱스 후보는1.524→1.021ms.6,000개 상태 전환의 WAL은 기존약16.28MB/두 인덱스약16.91MB였으며 checkpoint/FPI와 페이지 상태 영향을 받는다. 이 자료로 인덱스 유지 비용을 정당화하기 부족하여 이번 PR에서는 변경하지 않는다.

## 정확성과 검증

- C:101개 경계/같은 관측의 여러 예보/입력 중복/첫 중복 입력 탈락 후 두 번째 성공/도착 근거/기존 품질 조건 보존.
- D: 완료된 제외 편도만 종료/조사 중 및 정상 편도 유지/한 번500개와 다음 회차 잔여분/원본 보존 및 보정 표본 미생성/롤백 후 재시도.
- 동시성: 노선 잠금을 기다리는 동안 재조사가 시작되면 잠금 획득 후 재확인하여 PENDING 유지. 기존 동시 정산/초기화 경쟁/실패 롤백 테스트도 통과.
- 예보 모듈834개/마이그레이션15개 통과.

D는 기존 정산 트랜잭션 안에서 처리한다. 실제 제외가 있을 때만 노선 잠금을 얻으며, 뒤의 Writer와 잠금 순서가 뒤집히지 않도록 해당 노선 이하 ID를 오름차순으로 잠근다. 이 경로는 노선 잠금 보유 시점을 앞당길 수 있다. 읽기 자체의 회차별 최대 스캔 수는 이 PR에서 바꾸지 않았다.

## 배포/롤백

V28은 상태 CHECK의 허용 집합을 확장한다. 기존 검증된 집합이 새 집합의 부분집합이므로 NOT VALID로 등록하여 전체 평가 테이블 재검증을 피한다. 새 INSERT/UPDATE에는 CHECK가 적용된다. 별도 VALIDATE는 실행하지 않는다. lock_timeout1초 내 DDL 잠금을 얻지 못하면 마이그레이션이 실패한다.

QUALITY_EXCLUDED를 저장한 뒤에는 이를 모르는 이전 앱으로 단순 롤백하지 않는다. 새 상태를 읽을 수 있는 호환 버전으로 변경하거나, 별도 롤백 절차를 검토해야 한다. 임의로 전체 제외 평가를 PENDING으로 되돌리는 SQL은 제공하지 않는다. A/B/C만 되돌릴 때는 새 상태를 지원하는 D와V28을 유지할 수 있다.

운영 크레딧 개선은 아직 검증되지 않았다. 자동 배포/운영 설정 변경은 수행하지 않았다.
